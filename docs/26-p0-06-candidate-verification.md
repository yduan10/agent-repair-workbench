## 2. 候选格式和版本绑定

P0-05 的 `Edit.replacement` 是片段建议，没有行范围，绝不能当成全文件替换。T06 将其映射到**宿主冻结的唯一授权范围**：审核源码 `server.py` 的 `lookup_result` 函数四行（实际行号及 SHA 由固定 manifest 提供）。模型不能扩大范围。保留该范围之外每一个原始字节，最多 5 文件 / 64 KiB patch 的通用上限，本批 profile 进一步限制为 1 文件、单片段 8 KiB。

T06 请求包含 request_id、candidate_id、expected_baseline_hash、expected_file_hash 和结构化片段替换；运行 ID、角色、授权、suite 和磁盘根由宿主注入。拒绝路径穿越/绝对路径/软链接/特殊文件/非 UTF-8/二进制/陈旧版本/重复冲突请求。源码仅可解析，不在宿主 import 或 exec。解析完整候选 AST，只允许原签名 `lookup_result` 的函数体变化；禁止装饰器、签名变化、缩进逃逸和任何函数外节点变化。语义正确性仍由独立行为断言判断。

基线来自已审核源码快照，按整个文件及 manifest 哈希冻结；每份候选均从原基线创建，不叠加未验收的候选。新候选使用新 UUID 与序号（最多 2），其 ID+树 hash、基线 hash、suite hash、镜像 ID 和 oracle 版本绑定同一份比较报告。

所有文件先在宿主所有的临时 staging 中完整写入并 fsync，校验后原子重命名为新快照；失败不修改已提交版本。目录逐级拒绝软链接；正式快照只读。文件系统与 SQLite 不能视为同一事务：数据库先记录 preparing/请求摘要与所有权，再生成独占 staging，最后 CAS 提交元数据。崩溃留下 preparing 或孤儿快照时显式对账为 unknown，不自动重做应用或执行。去重键相同同参只返回旧结果，异参拒绝。

比较前后及每次下载前重新核对基线、候选、suite 内容 hash；任何变化使 verified 标签失效并拒绝提供旧标签下的新 diff。缓存不得跳过该核验。

## 3. 独立验收器：候选不能决定自己通过

权威 oracle 在可信宿主中运行，只通过有界 MCP stdio 通道与容器交互。不得将候选代码 import 到 oracle；不得运行候选的 pytest 插件、conftest、测试命令或信任其成功 JSON/JUnit/exit 0。

基线和候选分别在全新断网容器中运行，使用同一固定镜像、参数、输入顺序与冻结断言。原失败是 `wrong_type` 返回字符串 count；业务语义是当前会话已执行合法调用次数，每个合法 lookup 增加一次。固定回归覆盖首次及多次调用、整数边界输入、非法输入不计数、错误行为和严格结果契约。简单返回常量 1 或放宽 output schema 都不能通过。

每份快照分别跑 `wrong_type` 和 `pass`，共四个独立容器。每个 MCP 会话只初始化一次，冻结序列为合法 id=1 得到 count=1、非法字符串 id 被 -32602 拒绝且不计数、合法 id=0 得到 count=2、合法 id=-1 得到 count=3。声明 schema 前后核对，结果必须是严格整数（不接受 bool 或浮点数）。业务断言失败继续收集，协议失败后的必测项记 not_run。此有限黑盒验收只能证明冻结行为集，不声称证明任意程序语义或全部真实副作用。

被冻结的是宿主输入、期望及 oracle 代码版本。即使服务端宣称了更宽 schema，宿主仍用原契约验证实际结果，并核对声明未被替换。缺响应、协议错误、超时、非零退出、未执行完预期检查、任何必测项 skipped 均不能 candidate_verified。候选输出的额外字段/“全部通过”文本只是不可信数据。

必须同时满足：

1. 原始基线确实出现预期错误，否则 baseline_not_reproduced / inconclusive。
2. 候选原始失败通过。
3. 冻结回归全部完成并通过，无新增失败，不能按总成功数判断。
4. 基线/候选/suite/镜像/源码版本前后相同，资源清理已确认。

可信 controller 计算 candidate_verified；模型只能解释结果，不能写这个状态。candidate_verified 不等于用户已接受，当前不实现自动接受或写回项目。

## 4. 执行隔离与资源回收

复用 Docker 控制、MCP SDK 和有界传输基础；新增独立 P0-06 固定镜像/启动 profile，不放宽原 P0-03 无挂载策略。新 profile 仅挂载一个宿主创建并校验、只含固定 `server.py` 的独立快照目录到 `/opt/subject` 只读位置，无主目录、密钥、测试集或 Docker socket。

**执行入口与候选分离，宿主负责最终约束。** 镜像内固定 launcher 启动只读候选 worker；同 UID 的候选仍可能向 launcher 发信号，因此容器内监护器只是辅助回收机制，不是安全根。期限、强制停止、精确容器回收和验收判定均由宿主实施；不增加 root 或 CAP_SETUID。断网、非 root、cap-drop ALL、no-new-privileges、只读 root、CPU/内存/PID/输出/时间限制沿用已有规格。镜像提前显式准备，运行不自动 pull/build/install。

每次比较在外部操作前保存 attempt_id、两侧执行身份和请求摘要。取消/超时在有界 shield 内等待 MCP/子进程关闭及精确容器清理；原生重复 Task.cancel 也不能遗留后台任务。中断只对账，暂停的活 owner 不可被替代。无法确认清理则 outcome_unknown，禁止以部分通过掩盖未知。活动候选不能清理；P0 暂无自动删除候选策略。

宿主控制进程被 SIGKILL 是明确的故障窗口：候选可暂停同 UID 的容器辅助监护器，所以不继承 P0-03 的进程独立到期回收承诺。P0-06 持久登记全部执行身份，恢复后只读 inspect 并允许显式精确 reap；必须实测杀宿主后的残留发现与回收，未知期间不能验证通过。宿主存活时的期限和取消为硬门禁。若后续要承诺宿主死亡后的硬时间上界，须先交付独立宿主 watchdog/外部 lease reaper，并另作故障验收。

## 5. 存储、模型预算与 API

新候选记录与 P0-05 AnalysisSummary 分离，旧 summary v1 的 proposal_only 继续表示模型分析产出，不改写历史含义。候选记录引用真实 analysis task ID；修复运行自己的最终状态由可信比较器决定。新增 `RepairTask` / `RepairEvent` / `CandidateRecord` / `ComparisonRecord` v1 和 additive migration 0004～0006，使用新表；不扩展旧 `AnalysisEvent.tool` 枚举，也不继续已 finished 的旧 analysis。修复 CLI 从同一审核案例新建一个端到端修复 task；可引用已存在的 analysis ID 作为来源，但该引用不导入未持久的 replacement 或继承旧的已结束预算。修复任务自身从第一次模型请求到最终比较全程用同一个账本。数据库扩展迁移，不改已有表/枚举或自动迁移旧库。主库升级前停写、一致性备份、逐表保真核验。

候选/比较元数据至少包括：task/candidate/attempt ID、序号、阶段、结果、基线/候选/suite/oracle/镜像摘要、逐项安全规则结果、输入/输出 tokens、未知预留、费用未知、时间及关联 analysis ID。当前仅授权公开合成源码，因此可以保存有界 diff 和候选源码供复核；不因此开放私有文件持久化或保存任意模型原文。网页 JSON schema 严格，代码按文本转义呈现。

模型预算复用 P0-05b 的预算契约与 reserve/settle 校验逻辑，由新 RepairTask 账本持久保存；调用前预留且同一修复任务累计，不能通过重启子分析重置两候选/12 模型/20 工具/600秒限制。T06/T07 都计工具额度；每个实际模型请求和未完成尝试都计数。单个 repair task 生命周期持有独立 OS owner lock；每次请求、预算增量、候选序号/ID 及待执行身份通过同一 SQLite 事务和版本 CAS 登记。唯一键为 task/request；重复同参只读历史，不扣新额度、不重发；异参拒绝。T06 新建序号最多 2；T07 一次请求绑定 4 个已登记容器身份，逐项完成状态不能被旧 attempt 覆盖。上下文仅提供宿主核验的失败规则摘要和授权片段；oracle 原文及隐藏输入不进模型。修复角色只申请应用，验证角色只申请比较，工具执行及最终判定由宿主完成。

新增只读 GET 候选列表/详情/diff/比较结果，沿用精确本机 Host/Origin/no-store 与响应限额。没有 POST 模型/补丁/接受路由。网页“候选修复”和“回归验证”展示真实记录、差异、逐项基线/候选判定、失败原因、下一步 CLI 和未知费用；没有记录时提供可执行入口，不灌入开发测试数据。

## 6. 对照实验设计（b）

固定一个有业务 oracle 的开发案例先完成全部工程边界；另由 reviewer 在冻结 oracle 后提供独立保留变体，明确小样本不能代表泛化。每例单角色/三角色各三次独立尝试，交错顺序，使用同模型参数、可用工具权限总集合、相同源码范围、两候选/总 token/请求/时间上限。

单角色不能退化成无工具单轮 prompt；它也能取证、提出候选及获得相同可信比较反馈。三角色通过上下文与权限拆分执行同一任务。确定性检查只报告检出，修复率 N/A。报告每次结果、失败/未知、实际 token、用时、工具/模型次数；未配置单价则费用未知。效果不支持时不宣称多 Agent 更优，记录默认模式决定依据；样本太小则结论不确定。
