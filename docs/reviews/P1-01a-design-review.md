## 2. 生产事故风险推演

**D01：租约过期后旧执行者恢复。** 已提交接收/claim，旧进程在 dispatch 前暂停；120 秒后另一进程对账发现容器 absent，并按设计释放 Web 槽、接收新任务。旧进程恢复后继续调用 runner，两个 Web 运行可能同时存在。旧任务的 finish 最终被过期 lease 拒绝，也不能撤销已经发生的执行。影响单机 Web 并发上限和存储状态真实性。

## 3. 详细审计明细

### D01：恢复释放槽缺少旧执行者 fencing，已关闭

- 严重性：P1，`[confirmed]`，设计遗漏；维度 3 并发与资源安全。
- 位置：`docs/22-web-reproduction.md:32-35`。
- 实现依据：`run_store/execution.py:75` 在 claim 后执行；`run_store/store.py:377` 只在 finish 验证 lease。现有资源检查不能证明尚未 dispatch 的旧进程不会恢复。
- 最小修订：在 admit、dispatch、执行、清理和 finish 生命周期持有跨进程执行所有权锁；例如位于私有 state 目录、进程退出自动释放的文件锁。恢复流程必须先非阻塞取得同一把锁，再核对持久记录和资源；不能以 lease 过期代替所有者退出证明。锁忙保持槽忙，不重分派旧任务。允许采用具备同等可验证 fencing 的方案。
- 必测反例：W04 加入真实双进程暂停旧 owner、lease 过期、对账/新接收、恢复旧 owner；验证新接收不突破并发一，终态不被伪造。进程死亡与释放锁后的恢复单独验证。
- 修订复核：规格第 39-40 行已明确全生命周期持跨进程非阻塞 flock；CLI reconcile 同样取锁并保持到实时资源核对及状态事务完成；未取锁不登记 absent 安全证据。旧进程暂停时仍持锁，lease 过期不构成绕过理由；W04 第 68 行加入暂停 owner 的故障窗口。macOS/Linux 范围明确，不支持时拒绝执行。D01 设计缺口关闭，实现仍须通过该反例。
