## 4. B4审批设计必须保持的边界

- 审批绑定task/candidate/baseline/tree/oracle/suite/comparison及revision，不能只对候选ID记“接受”。
- 接受重新核对当前证据；其他候选或历史通过不能替代当前候选的有效比较。
- CAS确定有效决定，明确拒绝、撤销、改选候选与重复请求语义；append事件保存历史，不用last-write-wins覆盖。
- 下载为已核对候选的精确diff字节，不接受路径；审批/下载不调用Shell、不隐式写回项目。
- “已接受”只表示用户当时认可指定证据版本；后续版本失效显示历史已接受、当前需重验，不能伪称持续有效或已应用。
- W08–W10应加入审批检查与提交间证据变化、旧revision、新/旧候选交叉、下载关联与SHA反例。

### B1-2. 故障场景推演

**迟到创建穿透已释放槽**：父 Python 在发起 Docker create 后 SIGKILL，独立 docker 子进程或 daemon 操作未完成；新 worker 检查时容器尚不存在，旧计划被 reconcile，active 清零；新任务接收后旧 create 才完成。若用一次 absent 当终结证明，会产生遗漏资源并破坏单槽容器上限。范围为同状态目录网页槽；现有 task fence 只约束存活 Python owner，不证明 daemon 操作已结束。此为调用结构与设计可达时序分析，未执行真实故障注入。

### B1-3. 明细及最小修订

- **B1-D1 / Defect P1 / confirmed**：首轮 §6:110 与 §7:121。`runner/docker.py:83–125` 使用独立子进程，SIGKILL 不运行 finally；`candidate_execution/docker.py:109–169` 将 create 失败标为 unknown。`repair_recovery/service.py` 的 inspect 返回当前资源状态，不提供创建操作终结证明。最小修订：未知创建不能因一次或有限次 absent 自动释放；必须有正向终结证据，否则保持 active/recovery_required。固定等待不等于证明。新增“inspect absent 后旧 create 迟到出现”反例，验证零新任务/调用。
- **B1-D2 / Defect P2 / confirmed**：首轮 §3:61、§4:77。取消先于 consume 要同事务写 consumed 与 cancelled，但 `RepairStore.finish_task():842` 自开事务；只抽 `_create_task` 不能实现此约束。最小修订：再抽接收同一 Connection 的私有 finish helper，公开 CLI 包装保持原事务；receipt/终态/finished 事件同提交。注入每个写点失败，断言全有或全无、零执行。
- **B1-D3 / Defect P2 / confirmed**：首轮 §6:110、B1-11“一概缺报告拒绝”与 B1-12 恢复释放冲突。`reconcile_reproduction():334–366` 与 `reconcile_comparison():473–510` 将中断任务改为 unknown，却不会伪造缺失 report。最小修订：区分合法中断缺报告和已完成记录被删除报告；只有完整计划/身份/一致事件及资源终结证明足够时才释放合法中断记录，无法证明仍阻塞。将两种缺报告分列测试。
- **B1-D4 / Defect P3 / confirmed**：首轮 §5:93 引用“已有快照恢复规则显式清理”，当前 SnapshotStore 仅能在本次 `_publish` finally 清理自己的 staging，repair-recovery 处理容器/账本，没有未接收 baseline 孤儿清理入口。删去已有能力表述；可明确保留孤儿、禁止扫描删除，将显式清理另列后续范围。
