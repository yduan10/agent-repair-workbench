## 3. B1冻结前必须给出的契约

以下是下一批的设计输入，不要求当前就完成B2–B5代码：

1. **事务与状态矩阵**：初始RepairTask状态、接收/claim消费/模型预算预留的顺序、每个崩溃点可观察状态、同ID异参/墓碑/旧claim处理。请求ID与任务ID关系、指纹是否包含固定policy版本需明确。
2. **跨槽资源上限**：网页repair、analysis、reproduction同时执行的最大任务/容器/模型请求数；明确CLI是否计入同一限制，或作为明确独立边界。不能只写“各自一个槽”却不界定组合资源。
3. **owner与锁序**：修复全流程涉及的existing task fence与SQLite短事务顺序；取消在任务创建、claim消费、T05/T07之间竞争的结果；SIGSTOP不抢锁、SIGKILL后未知不重放。
4. **迁移**：新表、索引/唯一约束、旧库备份/保真、降级拒绝策略和无自动迁移；用真实SQLite验证，不仅mock库。
5. **失败响应表**：配置错误、槽忙、恢复待处理、版本失配、重复冲突的HTTP和安全枚举；202只能在持久接收完成之后返回。

B1必须给出可执行的W01–W07子集与旧CLI回归；表结构/执行控制器变动应在约2000行内独立评审。当前框架已明确要求这些前置，没有越过它们授权实施。

## 4. B4审批设计必须保持的边界

- 审批绑定task/candidate/baseline/tree/oracle/suite/comparison及revision，不能只对候选ID记“接受”。
- 接受重新核对当前证据；其他候选或历史通过不能替代当前候选的有效比较。
- CAS确定有效决定，明确拒绝、撤销、改选候选与重复请求语义；append事件保存历史，不用last-write-wins覆盖。
- 下载为已核对候选的精确diff字节，不接受路径；审批/下载不调用Shell、不隐式写回项目。
- “已接受”只表示用户当时认可指定证据版本；后续版本失效显示历史已接受、当前需重验，不能伪称持续有效或已应用。
- W08–W10应加入审批检查与提交间证据变化、旧revision、新/旧候选交叉、下载关联与SHA反例。

## 5. 测试与工程深度判断

W01–W12已覆盖一次执行权、持续取消、进程故障、真实迁移、审批CAS、下载字节与真实网页闭环；这些是独立于LLM主观解释的工程任务。必须区分确定性adapter、真实Docker、真实模型和浏览器证据，不能用mock执行终态代表工具执行成功。

此设计没有把当前补丁diff冒称确定性跨轨迹差异引擎，也没有将P1-02记忆混入本项。页面继续沿用UI-08中性、紧凑、结果优先布局，审批按钮只在其证据条件满足时出现/启用。
