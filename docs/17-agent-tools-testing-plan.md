# 产品闭环、Agent、工具与测试实施规格

任务：DOC-03 · 日期：2026-10-13 · 本文是 P0-05 / P0-06 的开发依据，不代表这些功能已经实现。

权威关系：遵循 [01 约束](01-constraints.md)、[04 质量门禁](04-quality-gates.md)；实现状态只由 [03 台账](03-roadmap.md)决定。本文统一职责、工具边界和验收编号；执行隔离与持久化细节继续以 [11](11-controlled-execution.md)、[14](14-run-store.md) 为准。

## 1. 我们交付什么

面向维护 Python Agent / MCP 工具的开发者及小型 AI 团队，解决一个可复查的开发任务：**工具调用失败后，复现问题、提出限定范围的修复，再用独立测试确认修复没有破坏旧行为。**

### 1.1 一次完整使用

1. 用户导入失败调用证据，或选择已审核的工具项目及版本；给定任务意图、允许修改的文件和资源预算。意图为 `check_only / diagnose / propose_repair`；P0-06 增加 `verify_candidate`。用户要修复时，发现契约错误只是证据，不能据此提前宣布任务完成。
2. 程序检查参数、结果 schema、错误标志与调用关联，必要时在受控环境复现。
3. 诊断 Agent 根据证据提出原因和可检验假设；请求检查的结果继续进入下一轮判断。
4. 修复 Agent 提出局部补丁；P0-06 起才允许应用到独立候选副本。
5. 验证程序对基线和候选执行同一套冻结测试；验证 Agent 解释通过项、失败项及未覆盖部分。
6. 用户拿到证据、diff、回归结果与成本，决定是否接受候选。系统不自动覆盖用户原项目或发布代码。

**具体案例**：固定版本 MCP 工具声明输出字段为 `user_id`，但序列化使用其他名称，真实输出违反契约。检查器定位不一致；诊断角色检查声明与序列化路径；修复角色按项目约定选择修复位置；验证器同时检查原始失败和其他输出场景。不能看到类型不符就盲目强制转换，也不能为了通过测试随意放宽公共 schema。

公开 SDK 历史问题已在 P0-02 复现，来源和固定版本见 [08](08-mcp-integration.md)；**尚未证明 Agent 能自动修复此案例**。某些源码片段或业务语义不足时，应给出缺失证据与拒判原因。

### 1.2 当前和目标的区别

| 能力 | 当前实现 | 后续交付 |
|---|---|---|
| JSON 契约检查、真实 MCP stdio 调用 | 已完成；外部工具限审核 profile | 新 profile 逐项审核与兼容测试 |
| 隔离执行、资源限制、故障注入 | 已完成受控本地 Docker 路径 | 候选副本及冻结验收，P0-06 |
| 运行状态、事件、报告、恢复对账 | 已完成本地 SQLite；显式对账不重放工具 | Agent 任务状态另行迁移，不能直接等同现有执行记录 |
| 三个产品 Agent / DeepSeek / LangGraph | 只有角色职责目录，尚未实现运行逻辑 | P0-05 只读协作；P0-06 实际候选闭环 |
| 网页 | 检查及真实运行记录可用；其他能力按目录显示状态 | P0-05/06 同步真实诊断/候选结果；网页发起和审批属 P1-01 |
| 项目记忆 | 尚未实现经验检索 | P1-02，人确认、有来源、可失效的经验 |

技术价值要由工程证据支撑：权限隔离、失败语义、可重现执行、不可篡改验收及相同预算的对照结果。使用多个提示词、包装第三方 API 或增加角色数量，均不能单独证明收益。

## 2. Agent 分工与协作

### 2.1 三个模型角色，一个程序控制器

| 角色 / 目录 | 输入 | 输出 | 可用能力 | 明确禁止 |
|---|---|---|---|---|
| 诊断 `agents/diagnosis/` | 安全证据、契约、已授权源码片段、复现结果 | finding / hypothesis / inconclusive；引用证据；待执行验证请求 | 读证据、读契约/源码，申请审核复现 | 修改源码、把猜测当根因、直接执行命令 |
| 修复 `agents/repair/` | 已定位问题、允许修改范围、相关源码、前一候选的失败摘要 | 结构化 patch proposal 或无法修复原因 | 只读工具；P0-06 申请应用局部补丁 | 修改基线、验收集、权限、预算；直接写用户项目 |
| 验证 `agents/verification/` | 原任务、冻结规则、候选 diff、程序测试结果 | 证据充分性、风险及未覆盖项说明 | 读证据；P0-06 申请固定比较 | 写最终通过状态、修改评分、把修复角色自评作为证据 |
| 控制器 `orchestration/` | 类型化任务配置和角色输出 | 状态转移、分派、权限决定、预算记账 | 在权限网关后调用实际工具 | 不作为第四个 LLM；不把安全决策交给提示词 |

每个角色独立 `contracts.py`、`agent.py`、`prompts/`、`tests/`，共享模型网关、执行器和存储；目录规范见 [09](09-agent-modules.md)。本表是权限上限，实际注册表按阶段进一步收紧。

验证角色使用新上下文，读取原问题及工具证据，不继承诊断/修复的隐藏推理或“已经成功”的自述。同一模型的错误仍可能相关，独立角色不等于统计独立。

### 2.2 决策与停止规则

```text
输入预检 → 确定性检查
  ├─ 输入不合法 / 环境不支持 → 明确失败或无法判断
  ├─ check_only 目标已满足 → 直接出检查报告
  └─ 需要上下文判断 → 诊断 → 受控补充证据 → 候选建议
       P0-05：验证角色检查证据与建议 → proposal_only（结束）
       P0-06：应用到副本 → 冻结比较
                ├─ 原失败解决且固定回归全部通过 → candidate_verified
                ├─ 有明确可改进证据且仍有预算 → 再提出一次候选
                └─ 超限 / 未知 / 无证据 / 仍失败 → 停止并保留结果
```

- 一次任务默认总时限 600 秒，最多两份候选；总时限包含模型、工具及清理。每个执行子步骤仍使用既有更小的时间/资源上限。
- 检查发现问题后，是否继续由任务意图决定；`diagnose/propose_repair` 不能以“检查器已经报错”为理由跳过用户要求的分析。完全由确定性证据满足目标时可以不用模型，但必须说明任务目标的完成依据。
- P0-05 首版串行分派；每任务最多 12 次模型请求、20 次受控工具请求，任何失败尝试也计数。此为开发初始上限，变更需回归及配置版本，不是性能承诺。
- `max_total_tokens`、每请求 `max_output_tokens` 必须显式配置。调用前预留输出预算，并计入完整输入的保守上界；估算方法及误差边界须随模型适配测试。无法给出安全上界时拒发请求，不以字符数随意假装精确 token 数。
- provider usage 缺失时保留预留额度，标实际消耗/金额未知；不能释放额度后继续无界调用。价格表缺失也不编造金额。
- 非法模型结构最多一次纠正请求，计入上述预算；网络超时不自动重复模型请求，避免未知计费叠加。返回自然语言不能绕过输出 schema。
- 模型建议无证据、固定规则被篡改、越权、取消或预算耗尽时停止；外部操作结果未知不自动重试。
- `proposal_only`、`candidate_verified` 是后续分析/候选结果类型，**不是当前 P0-04 的 run status**。`candidate_verified` 不等于用户已接受。
- P0-05 不承诺跨进程恢复模型循环。中断保留已提交步骤、未返回的调用标未知；不自动从 checkpoint 重发调用。P0-04 的 120 秒执行 lease 不能直接覆盖 600 秒 Agent 任务：P0-05 需独立任务/步骤持久化规格与迁移评审，或限定为前台协调、逐步使用现有短执行记录，不能静默改大旧 lease。

首版采用后者：前台串行协调，逐步关联现有短执行记录；新的 Agent 摘要存储格式和只读展示接口在 P0-05 设计子项冻结。暂停/恢复/网页审批不借此提前完成。

## 3. 三种容易混淆的“工具”

1. **被测工具**：用户的 MCP server / 工具项目。它可能有 bug，其描述和输出都是不可信输入。接入它是为了检查它，不等于授予产品 Agent 任意调用权限。
2. **Agent 受控工具**：我们定义的读证据、复现、补丁和比较接口。模型提出调用请求，宿主先验证权限和预算，再执行。
3. **基础组件**：MCP SDK、LangGraph、Docker、pytest、SQLite 等，是编程库、引擎或基础设施；不能计成五个“自研 Agent 工具”。

首版内部受控工具用严格 Python 接口注册到模型网关；**不必先把每个内部函数再包装成 MCP server**。对外被测工具通过官方 MCP SDK 接入。只有存在外部客户端复用需求时，才增加内部工具的 MCP 暴露层，并保持同一权限网关。

## 4. Agent 工具目录与契约

以下名称是待实现的逻辑 API，不是当前已有 CLI 子命令。P0-01～04 的底层能力可复用，但角色可调用的网关仍属 P0-05/06。

### 4.1 所有工具的共同契约

- 请求包含 `schema_version`、`request_id` 与工具参数；`task_id/role/权限/预算/根目录` 由宿主上下文注入，模型传入同名权限字段即拒绝。
- 所有对象拒绝未知字段，标识符、枚举、字符串和列表长度有界。源码每次最多 200 行 / 16 KiB；每次结果最多 64 KiB，过长返回明确截断标记及后续引用，不能静默丢失错误结论。
- 响应包含 `status`、`error_code`、`evidence_refs`、`observed_versions`、`truncated` 与类型化 payload。`status` 为 `ok / rejected / failed / outcome_unknown`；业务检查 pass/fail/not_checked/inconclusive 放 payload，**工具执行 ok 不等于被测对象通过**。
- 错误至少区分 `INVALID_INPUT / PERMISSION_DENIED / STALE_VERSION / BUDGET_EXCEEDED / RESOURCE_LIMIT / TOOL_FAILURE / RESULT_UNKNOWN / ARTIFACT_MISMATCH`，错误消息不携带原始值或密钥。
- 证据引用指向宿主生成的不可变 ID+摘要；模型不能自行发明一个 evidence ID 就获得“已验证”标签。网关核对归属、版本、存在性。
- 可持久化报告沿用安全元数据限制。授权源码片段/原始值只在受控临时上下文使用，不写日志/报告；下一节规定模型外发边界。

### 4.2 工具清单

| ID / 工具 | 输入 → 输出 | 权限与实现边界 | 可调用角色 / 迭代 |
|---|---|---|---|
| T01 `read_evidence` | `evidence_id, section` → 脱敏检查项、事件、来源/摘要 | 只读已授权任务；拒绝跨任务 ID，不读任意数据库记录 | 三角色 / P0-05 |
| T02 `read_contract` | `profile_id, tool_name, revision` → 固定输入/输出 schema 与版本 | 只读已审核快照；动态发现也必须经过 profile 权限和大小检查 | 三角色 / P0-05 |
| T03 `read_source` | `snapshot_id, relative_path, start_line, end_line` → 片段及文件摘要 | 仅授权文件，拒绝绝对路径、越界、软链接和密钥文件；版本变化拒绝 | 三角色 / P0-05 |
| T04 `check_contract` | `case_id, contract_revision` → 程序检查报告引用 | 复用 checker；case 引用解析由宿主完成，不允许模型篡改原始失败证据 | 诊断、验证 / P0-05 |
| T05 `request_reproduction` | `approved_case_id, profile_revision` → 短执行 ID、结果引用 | 只允许任务已授权的只读或隔离 fixture；固定 argv/env/image，不接受 shell；真实 SDK/Docker 执行 | 诊断、验证 / P0-05 |
| T06 `apply_candidate_patch` | `candidate_id, expected_tree_hash, patch` → 新摘要、diff 或拒绝 | 仅候选副本白名单；先完整验证再应用；禁止验收集/依赖锁/符号链接/目录穿越/二进制；首版 patch ≤64 KiB、≤5 文件 | 修复 / P0-06；P0-05 不注册 |
| T07 `compare_candidate` | `candidate_id, baseline_hash, suite_id, suite_hash` → 基线/候选逐项结果、程序结论 | 唯一验收器读取冻结规则；选择既定命令，不执行模型提供的测试命令 | 验证 / P0-06；P0-05 不注册 |
| T08 `lookup_experience` | `project_id, tool_revision, error_code` → 经确认的适用经验及来源 | 项目/版本/失效过滤，记忆不能改变权限；写记忆由人工确认流程处理 | 诊断、修复 / P1-02 |

角色的候选建议、最终解释使用结构化角色输出，不为它们额外造一个“写最终成功状态”的 tool。取消、配额修改、删除记录、用户接受补丁由应用控制，不开放给模型。

### 4.3 副作用与重复请求

- T01～04/08 是读或纯计算；相同请求可以返回相同版本结果，缓存键含版本/权限域。
- T05 会创建执行资源：先持久化 attempt 再分派；重复 `request_id` 返回同一 attempt，不再次启动。若是否分派无法确定，保留 unknown，不能仅凭数据库无结果重新调用。
- T06 以 `(task_id, candidate_id, request_id)` 去重，保存补丁摘要；相同 ID 不同内容拒绝。临时目录完整应用、校验后提交候选版本；失败候选不覆盖上个版本。
- T07 会启动测试，复用执行生命周期和去重规则。基线可缓存，但环境/源码/用例/验收器任何版本变化必须失效。
- 不承诺第三方工具 exactly-once。涉及真实外部写副作用的 profile 不在 P0 自动执行范围。

### 4.4 模型上下文与源码外发

P0-05 的真实模型验收只使用审核过的公开案例或合成数据。已有网页本地导入继续保持本地，不因为接通 DeepSeek 自动上传。

私有项目模型调用必须由用户显式启动并选择允许发给模型的文件/片段范围；原始调用值默认禁止外发。密钥文件、环境变量及凭据永不进入上下文；脱敏程序只能作为辅助，不能承诺识别全部秘密。模型输入组装基于白名单片段及安全证据，并可让用户在本地检查发送范围。批准前只能做本地确定性检查。

T03 读授权快照不等于默认批准外发；模型网关再次执行发送策略。原始模型响应、源码与提示词全文不默认进入 trace；记录 prompt 版本、模型标识、调用 ID、预算及安全结构化结果。调试保存原文需后续单独设计，P0 不开放。

## 5. 哪些复用第三方，哪些自己做

| 层 | 复用内容 | 本项目必须实现和测试的内容 |
|---|---|---|
| MCP | 已锁官方 Python SDK：握手、协议对象、会话 | profile 审核、字段映射、错误分类、权限、单次调用及未知结果处理 |
| 编排 | P0-05 引入 LangGraph 的图执行基础 | 类型化状态边、角色权限、有限循环、预算、停止规则；不依赖模型自觉遵守 |
| 模型 | 用户现有 DeepSeek 兼容接口 | 统一请求/输出契约、额度预留、usage 缺失、超时/取消、脱敏策略；不训练或更换模型 |
| 检查与测试 | jsonschema、pytest、Hypothesis | 支持的契约语义、证据归一化、真实失败样例、冻结 oracle、基线/候选比较 |
| 隔离执行 | Docker / 操作系统进程与资源机制 | 安全配置、所有权标记、生命周期、取消/清理、故障证据；不自写容器引擎 |
| 状态 | SQLite、SQLAlchemy、Alembic | 业务状态、事务/CAS、租约、去重、报告完整性、恢复和保留策略 |
| UI | Next.js / React、Playwright、axe | 诊断证据、候选 diff、真实回归、成本及错误状态等产品流程 |
| 记忆 | P1 首版复用 SQLite 条件查询 | 经验来源、人工确认、适用范围、失效/删除和污染防护 |

**可以接第三方 MCP server，但需要具体用途：**

- 已审核的第三方 MCP 工具项目可以作为被测对象；固定源码/依赖/工具声明后接入，不意味着其全部工具都能执行。
- GitHub 只读源码/issue、文档检索可作为以后补充证据的外部连接器，优先复用维护中的客户端或 MCP 实现；当前 P0 已有本地源码快照，无需为凑工具数提前接入。若引入，新增任务必须覆盖凭据、网络目的地、限流、失败/注入测试。
- 通用 Shell MCP、无限文件系统 MCP、自动安装未知 server、自动发 PR/comment、浏览器自由操控不是本阶段必要依赖。即使第三方提供，也不能绕过我们已有权限和冻结验收。

MCP 传输版本扩展按 P2-01；不自研 JSON-RPC 协议框架。第三方实现也可能出错，因此依赖版本固定和适配测试是本项目责任。

## 6. 测试用例如何定义

### 6.1 三层数据，不混算

| 数据集 | 用途 | 来源与可见性 |
|---|---|---|
| 工程契约/故障集 | CI 验证状态、权限、预算、清理 | 合成输入、固定 seed；开发者可见；不计真实业务准确率 |
| 已复现公开问题 | 验证真实工具兼容与修复 | URL、固定 commit、依赖摘要、真实复现报告；修复 oracle 需独立确认 |
| 独立保留集 | 评估泛化、回归与多角色收益 | 不用于调 prompt；reviewer 编制或保留，开发阶段不开放答案；泄漏后重新分组并披露 |

每例均记录以下字段；作为待实现 `CaseManifest` 的必填设计，不冒充现有可运行格式：

```yaml
schema_version: 1
case_id: contract-output-alias-001
source_kind: synthetic        # synthetic / public_historical / external_integration
source_ref: fixtures/alias_case
source_revision: <fixed-tree-sha256>
profile_id: <reviewed-profile>
environment_digest: <locked-image-and-dependencies>
failure_class: output_schema_violation
input_ref: <local-authorized-evidence-id>
baseline_assertions: [original_case_fails_with_expected_code]
candidate_assertions: [original_case_passes, fixed_regressions_pass]
forbidden_changes: [acceptance_suite, baseline, dependency_locks]
oracle_revision: <reviewed-suite-sha256>
seed: 17
repairability: repairable     # repairable / must_abstain / unknown
split: development           # development / holdout
```

以上占位值必须在运行前解析并校验，不能使用字面占位符运行。`source_ref` 与预期 oracle 不由模型提供；公开问题关闭状态不是正确答案。业务含义无法确认的案例不能自动标 `repairable`。

冻结测试至少包含：原始失败、正常边界、历史行为、错误处理、越权/泄漏反例。测试文件在修复容器不可写，宿主验收器在执行前后核对摘要；模型生成的新测试只能补充，不能替代固定集。

**仅只读挂载和文件hash不够。** P0-06 权威oracle在可信宿主/独立验收进程运行，通过受限 MCP 通道黑盒调用隔离基线和候选，由验收器对实际返回数据进行断言。不能把候选源码 import 到权威oracle进程，不能让候选控制 pytest 插件、用例收集、断言代码或判定结果。候选打印的“成功”、JUnit/JSON报告、退出0均只是待分析数据，不是最终通过证明。项目内部pytest可作额外诊断；若必须验收的行为无法从该边界独立验证，结果为未完成，不以同进程测试的绿灯补齐。新增 R11 覆盖这一不修改文件的逃逸方式。

### 7.2 工程门禁与效果指标分开

- **工程门禁**：A/R 矩阵适用项全部通过；任何越权、泄漏、验收篡改或失败误报通过均阻断。静态检查、版本锁、独立评审及修复后复审完成。
- **效果评估**：按 04 报告诊断精度/覆盖率、正确修复率、回归率、tokens/耗时/人工步骤；不能拿工程测试通过数换算成模型准确率。
- **比较方式**：确定性检查、单 Agent、三角色三组；模型两组有相同工具权限集合与总预算、同一模型/参数。每例三次独立尝试，保留模型非确定性及全部失败；训练/调 prompt 和保留集分离。程序组不做修复时该指标 N/A，不能人为记零来抬高模型收益。
- **取舍规则**：首先满足同一权限/验收门禁；在保留集上比较每例正确修复数与成本。三角色若没有可重复质量收益，也没有可量化审阅成本收益，就不默认启用三角色；小样本差异标不确定。结果不支持时简化角色，而不是降低基线工具能力。
- **规模**：P0 以完整边界和可复现闭环为门槛，不编造商业准确率目标。P1-03 至少三个不同工具项目，至少一个不是开发 fixture；P1-04 至少十个有来源故障，真实和合成分报。这些是已定计划，不能用三份同类 fixture 代替。
